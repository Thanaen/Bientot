# CI quality gates

The `CI` workflow runs for pull requests and pushes to `main`. It has these jobs:

- `Plan` runs on Ubuntu. It decides which of the jobs below the run needs.
- `Rust` checks formatting, runs clippy with warnings as errors, and runs the tests of the Cargo workspace on Ubuntu. When the app can look different, it also renders the flyout of every demo scenario in French and English, light and dark, with Mesa's software Vulkan driver.
- `Rust on Windows` tests `bientot-store` and `bientot-windows`, builds the release executable of `bientot-app` with its `release` feature (the usage signal), as the Store package and the ZIP ship it, checks that its version resource names it « Bientôt » (`FileDescription` and `ProductName`, which Task Manager and the Startup apps page show), checks that the Velopack build (`direct` feature) compiles, measures the v1 gates (size under 20 MB, ready in under 1 s, under 60 MB of memory) on a throwaway `--data-dir`, so that the run sends no usage signal, builds the portable ZIP and the MSIX from it with `scripts/package-rust.ps1` (each under 20 MB), installs the unsigned MSIX and uninstalls it, and uploads the executable for 7 days. Only the size fails the job: a hosted runner has no GPU, so its time and memory are indications. `scripts/measure-performance.ps1` then measures the spec budgets (SC-007) with the built-in activity source: it warns above them and fails only above 2 % CPU, 200 MiB or 6 s.
- `Record tested tree` records the tree that passed, for the push to `main` that follows the merge.
- `Publish screenshots` pushes the screenshots that `Rust` rendered to the `refs/ci-screenshots/<pull request>` ref, outside the branches so that Vercel does not try to deploy it. The job summary links to each screenshot.

A successful `CI` run requires every job that runs to pass.

## When each gate runs

`Rust` runs for a pull request only when it changes a Rust file (`crates/`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`), `packaging/` (the MSIX manifest and the license texts the tests read) or `.github/workflows/ci.yml`. A pull request that changes only documentation or the web service runs no Rust job.

`Rust on Windows` runs only when a pull request changes `crates/bientot-app/`, `crates/bientot-windows/`, `crates/bientot-store/` (its file handling behaves differently on Windows), `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `packaging/`, `scripts/measure-performance.ps1`, `scripts/package-rust.ps1`, `scripts/verify-package-executables.ps1` or `.github/workflows/ci.yml`, and only after `Rust` passed. Both Rust jobs cache their dependency builds with `Swatinem/rust-cache`; a pull request's cache serves only that pull request's later pushes.

`Rust` renders screenshots, and `Publish screenshots` publishes them, only when a pull request changes `crates/bientot-app/` or `.github/workflows/ci.yml`. Pull requests from forks still render them, but do not publish.

For a pull request, `Record tested tree` runs once every other job has passed or was skipped, and records the tree of the tested merge commit as the `tested-tree-<attempt>` artifact, retained for 30 days. When a push to `main` comes from a merged pull request, `Plan` looks for a successful pull request run of that pull request's last head that recorded the pushed commit's exact tree. When it finds one, the push run skips both Rust jobs, because the same files already passed every gate. When `main` moved after the last pull request run, the trees differ and the push run runs every gate. A direct push, a missing artifact, or an API error also runs every gate.

## Releases

The `Release` workflow (`.github/workflows/release.yml`) publishes the Velopack installer and update packages as a GitHub Release tagged `v<version>` and titled `Bientôt <version>`. It runs every night at 04:17 UTC and does nothing when the commit at the head of `main` already has a release. For an urgent fix, run it from the Actions tab (**Run workflow**). A Windows runner builds the release with `scripts/release-direct.sh`, which computes the delta from the latest release in the feed at `https://worktime.thanaen.dev/updates/`. vpk names the files after the packId, `Thanaen.WorkTime`, which installed copies update by, so the workflow keeps those names and also publishes the installer and the portable ZIP as `Bientot-Setup.exe` and `Bientot-Portable.zip`. A separate job, the only one with write access, attests the build provenance of every file (`actions/attest`, see [code-signing.md](code-signing.md#where-the-builds-come-from)), adds that attestation to the files as `Bientot.intoto.jsonl`, uploads the files to a draft and publishes it as the latest release once every file is uploaded. Its notes start with the files added to `scripts/release-announcements/` since the previous release, then follow with the ones GitHub generates, from which `scripts/release-notes.sh` removes the pull requests that do not change the app (see CONTRIBUTING.md, "Commits and pull requests"). `scripts/package-rust.ps1` builds the portable ZIP and the MSIX for the Microsoft Store.

The `Store package` workflow (`.github/workflows/store-package.yml`) runs only from the Actions tab, on `main`. It builds the Store MSIX, versioned `<major>.<minor>.<commit count>.0`, and keeps it as the `bientot-store-msix` artifact for 30 days. Its `Submit` job then sends the package for certification with the Microsoft Store CLI: `msstore publish --noCommit` puts the package in a new draft, the job replaces the draft's listing texts (title, descriptions, features, keywords, release notes, copyright, license terms and developer name, in English and French) with those of `packaging/store/listing.json`, and `msstore submission publish` submits it. Screenshots and the other images stay as they are in Partner Center. Update the release notes in that file before a submission. That job runs in the `release` environment and is the only one that reads the Partner Center credentials: the `MSSTORE_TENANT_ID`, `MSSTORE_CLIENT_ID`, `MSSTORE_CLIENT_SECRET` and `MSSTORE_SELLER_ID` secrets of an Entra application with the Manager role in Partner Center. Set them as secrets of the `release` environment, not of the repository, and give that environment required reviewers and a deployment rule that allows only `main`: GitHub creates the environment without any protection the first time a job refers to it, so the approval exists only once those rules are set. When one of the secrets is missing, the job submits nothing and says so in the run summary, and the artifact is uploaded in Partner Center by hand. Clear **Submit the package to the Store** to build the package only. The workflow does not run every night like the direct channel, because each submission goes through certification first. `msstore publish` deletes any submission draft that is not published yet and starts a new one from the last published submission, so a run discards listing or package changes made by hand in Partner Center and not yet submitted, and listing texts edited in Partner Center are overwritten by the file at the next submission.

The `Store listing` workflow (`.github/workflows/store-listing.yml`) also runs only from the Actions tab, on `main`, in the `release` environment. It reads the current submission with `msstore submission get` and changes nothing in Partner Center. It prints the submission, with signed upload URLs removed, and keeps it as the `store-submission` artifact for 7 days. It also compares the listing texts with `packaging/store/listing.json` and shows any difference in the run summary. Run it to check the Partner Center secrets, or before a submission to see whether a text was edited in Partner Center and not in the file.

## Scorecard

The `Scorecard` workflow (`.github/workflows/scorecard.yml`) runs [OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/Thanaen/Bientot) on each push to `main` and every Monday, since a change to the repository settings pushes no commit. It lists the failed checks as code scanning alerts in the Security tab and publishes the score that the README badge shows. It does not run for pull requests and blocks nothing. Scorecard's API accepts the published results only from a workflow without top-level `env`, `defaults` or write permissions, whose job runs on Ubuntu and uses only `actions/checkout`, `actions/upload-artifact`, `github/codeql-action/upload-sarif` and `ossf/scorecard-action`: keep it that way.

## Required checks

Configure `Rust` and `Rust on Windows` as required checks on `main`. A skipped job counts as passed, so a documentation-only pull request is not blocked.
